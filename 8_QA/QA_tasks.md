# Задания по оценке качества

## Задание 1. Разработка метрик качества программного продукта

Цель работы: Научиться разрабатывать **измеримые метрики качества** программного продукта на основе модели качества из ГОСТ Р ИСО/МЭК 25010-2015

1. **Выбор характеристик качества** — определение того, *какие аспекты качества* важны для продукта.
2. **Детализация через подхарактеристики** — уточнение выбранных характеристик до конкретных, однозначно трактуемых свойств.
3. **Разработка метрик** — определение способов измерения и проверки каждой подхарактеристики.


### Шаг 1. Выбор характеристик качества

Выберите **4–6 характеристик**, которые наиболее важны для вашего типа проекта. Для каждой выбранной характеристики укажите:

1. **Почему эта характеристика критична** для вашего проекта (1–2 предложения).
2. **Какие риски возникают** при низком уровне этой характеристики.

Для **невыбранных характеристик** кратко объясните, почему они не приоритетны.

#### Пример (вариант A — веб-сервис для совместной работы)

| Характеристика | Выбрана? | Обоснование |
|----------------|----------|-------------|
| Функциональная пригодность | ✅ Да | Без правильных функций сервис бесполезен |
| Надёжность | ✅ Да | Пользователи не простят потерю данных или частые сбои |
| Эффективность производительности | ✅ Да | Долгие ответы убивают опыт совместной работы |
| Удобство использования | ✅ Да | Интерфейс должен быть интуитивен для разных пользователей |
| Безопасность | ✅ Да | Совместная работа → чужие данные, нужна авторизация |
| Совместимость | ❌ Нет | Веб-сервис работает в браузере, интеграции не планируются |
| Сопровождаемость | ❌ Нет | Студенческий проект, долгосрочная поддержка не нужна |
| Мобильность | ❌ Нет | Только десктопные браузеры, мобильной версии не будет |

### Шаг 2. Детализация через подхарактеристики

Каждая характеристика качества состоит из **подхарактеристик**, которые уточняют, *что именно* мы оцениваем.

**Полный список подхарактеристик по ГОСТ 25010**

| Характеристика | Подхарактеристики |
|----------------|-------------------|
| Функциональная пригодность | Полнота (completeness), правильность (correctness), соответствие задачам (appropriateness) |
| Надёжность | Устойчивость к ошибкам (maturity), доступность (availability), отказоустойчивость (fault tolerance), восстанавливаемость (recoverability) |
| Эффективность производительности | Временное поведение (time behaviour), использование ресурсов (resource utilization), пропускная способность (capacity) |
| Удобство использования | Узнаваемость пригодности (appropriateness recognizability), обучаемость (learnability), управляемость (operability), защита от ошибок (user error protection), эстетика интерфейса (UI aesthetics), доступность (accessibility) |
| Безопасность | Конфиденциальность (confidentiality), целостность (integrity), неотказуемость (non-repudiation), подотчётность (accountability), аутентичность (authenticity) |
| Совместимость | Сосуществование (co-existence), оперативная совместимость (interoperability) |
| Сопровождаемость | Модульность (modularity), повторяемость использования (reusability), анализируемость (analysability), модифицируемость (modifiability), тестируемость (testability) |
| Мобильность | Адаптируемость (adaptability), устанавливаемость (installability), заменяемость (replaceability) |

Для **каждой выбранной характеристики** выберите **2–3 подхарактеристики**, которые наиболее точно отражают важные для вашего проекта аспекты качества.

**Для каждой подхарактеристики** дайте **операциональное определение** — своими словами, что именно она означает в контексте вашего проекта.

#### Пример (продолжение — веб-сервис)

| Характеристика | Подхарактеристика | Операциональное определение (в контексте проекта) |
|----------------|-------------------|---------------------------------------------------|
| Надёжность | Доступность (availability) | Сервис доступен и отвечает на запросы пользователя |
| Надёжность | Отказоустойчивость (fault tolerance) | При сбое одного компонента (например, базы данных) сервис продолжает работать или корректно сообщает о проблеме |
| Надёжность | Восстанавливаемость (recoverability) | После сбоя сервис возвращается в рабочее состояние без потери данных |
| Эффективность производительности | Временное поведение (time behaviour) | Время отклика интерфейса и API не превышает приемлемых значений |
| Эффективность производительности | Использование ресурсов (resource utilization) | Сервис не потребляет чрезмерно CPU/память на сервере и в браузере |
| Удобство использования | Обучаемость (learnability) | Новый пользователь может выполнить основные действия без чтения документации |
| Удобство использования | Защита от ошибок (user error protection) | Пользователь не может случайно удалить важные данные без подтверждения |

Для каждой выбранной характеристики — таблица с подхарактеристиками (2–3) и операциональными определениями.

**Итого:** минимум 8–12 подхарактеристик.

### Шаг 3. Разработка метрик

Теперь для **каждой подхарактеристики** нужно разработать **1–2 метрики** — конкретный способ измерить, соответствует ли продукт требованиям.

### Структура описания метрики

```markdown
#### Подхарактеристика: [Название]

**Метрика:** [Название метрики]

- **Способ измерения:** [автоматический / ручной / экспертный / пользовательское тестирование]
- **Единица измерения:** [секунды, проценты, количество, бинарное да/нет, шкала 1–5]
- **Целевое / приемлемое значение:** [конкретное число или диапазон]
- **Метод / формула расчёта:** [как именно получаем значение]
- **Условия проведения измерения:** [при какой нагрузке, данных, окружении]

**Пример (для подхарактеристики «Восстанавливаемость»)***

> **Метрика:** Время восстановления после принудительного завершения процесса (RTO — Recovery Time Objective)
> - **Способ измерения:** автоматический
> - **Единица измерения:** секунды
> - **Целевое значение:** ≤ 30 секунд
> - **Формула расчёта:** время от момента завершения процесса до момента, когда сервис отвечает на health-check запрос с кодом 200
> - **Условия:** тестовые данные объёмом 1000 записей; принудительное завершение процесса через `kill -9`; замер производится 5 раз, берётся среднее

```
