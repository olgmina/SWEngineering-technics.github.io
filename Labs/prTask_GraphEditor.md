# Графический редактор

Программа предназначена для рисования по точкам и добавлять, редактировать фигуры
а) отрисовывать точки движения мыши выбранными "карандашами" (растровый редактор);
б) изменять параметры заготовленных фигур (векторный редактор)
в) допускать изменение и перемещение, сохранение с возможностью последующего редактирования группы фигур
 
Проект проходит через 3 инкрементных стадии:

1. **Растровый редактор** — рисование мышью, повторение ООП, UML классов, абстрактный класс и фабрика.
2. **Векторный редактор** — представление фигур в виде полигонов, добавление заливки, контура и тени с помощью декоратора.
3. **Рисунок как составной объект** — объединение объектов, выбор формата, сохранение и чтение.

При этом вместе с функциональностью постепенно формируются практики программной инженерии:

- управление разработкой: Git, ветки, commit, Pull Request, Code Review, Release;
- проектирование: UML классов и последовательностей, 
- паттерны: Абстракный суперкласс, фабричный метод, Хранитель, Прототип, Декоратор;
- создание программного продукта: подсказки, сериализация, настройки;
- контроль качества: соотвестие артефактов проекта коду, оценка простоты внесения изменений, ;
- документация проекта:  Readme, changelog, \docs.

## 1. Функциональные требования 

| ID | Функциональное требование | Описание | Критерий приёмки |

| **FR-1.5** | Отображение элементов | Программа должна отображать созданные элементы на рабочей области | Все созданные элементы видимы и соответствуют заданным параметрам |

| **FR-1.8** | Очистка изображения | Пользователь должен иметь возможность удалить все созданные элементы | После выполнения команды очистки рабочая область не содержит созданных элементов |
| **FR-1.9** | Выбор инструмента в процессе работы | Пользователь должен иметь возможность изменить выбранный инструмент | После смены инструмента создаются элементы нового выбранного типа |

## 2. Архитектура приложения

на объектной модели, в которой различные элементы изображения представлены объектами общего абстрактного типа.

1. Предлагается выделить следующие основные компоненты:

```text
                  GraphEditor
                      │
              ┌───────┴────────┐
              ↓                ↓
           Canvas          ToolSelector
              │
              ↓
         PixelFactory
              │
        ┌─────┼─────┐
        ↓     ↓     ↓
      Point Circle Square
```

Все элементы изображения должны иметь [общий абстрактный базовый класс](https://sites.google.com/view/study-pattern/%D0%B3%D0%BB%D0%B0%D0%B2%D0%BD%D0%B0%D1%8F/%D0%B7%D0%B0%D0%B4%D0%B0%D1%87%D0%B8/task-1-%D0%B0%D0%B1%D1%81%D1%82%D1%80%D0%B0%D0%BA%D1%82%D0%BD%D1%8B%D0%B9-%D1%81%D1%83%D0%BF%D0%B5%D1%80%D0%BA%D0%BB%D0%B0%D1%81%D1%81), например Pixel

```text
             <<abstract>>
                 Pixel
                   △
          ┌────────┼────────┐
          │        │        │
        Point    Circle    Square

```


2. Создание конкретного элемента изображения должно быть вынесено в [фабрику](https://sites.google.com/view/study-pattern/%D0%B3%D0%BB%D0%B0%D0%B2%D0%BD%D0%B0%D1%8F/%D0%B7%D0%B0%D0%B4%D0%B0%D1%87%D0%B8/task-2-%D1%84%D0%B0%D0%B1%D1%80%D0%B8%D1%87%D0%BD%D1%8B%D0%B9-%D0%BC%D0%B5%D1%82%D0%BE%D0%B4).
```text
Tool
 ↓
PixelFactory
 ↓
Pixel
 ↓
Point / Circle / Square
```

Рабочая область отвечает за отображение созданных элементов.
Она не должна содержать логику создания каждого конкретного типа элемента.
Предполагается разделение ответственности (действия пользователя, Инструмент, Графический примитив)

# Инкремент 2. Векторный редактор

реализовать фигуру в виде полигона и обеспечить возможность независимо добавлять к ней:

- заливку;
- контур;
- тень.

Фигура должна содержать не менее трёх вершин.

Пример:

```text
P1 ●────────● P2
    \        \
     \        \
      \        ● P3
       \      /
        ●────●
```

Положение и форма фигуры определяются координатами её вершин.

Новая функциональность должна быть добавлена без нарушения возможностей первого инкремента.

## 2. Архитектурная спецификация

**Архитектурная проблема**

На первый взгляд дополнительные свойства фигуры можно реализовать наследованием.

Например:

```text
Polygon
   △
   ├── FilledPolygon
   ├── BorderedPolygon
   ├── ShadowedPolygon
   ├── FilledBorderedPolygon
   ├── FilledShadowedPolygon
   ├── BorderedShadowedPolygon
   └── FilledBorderedShadowedPolygon
```

Однако количество классов быстро увеличивается с каждой новой комбинацией свойств.

Поэтому необходимо обеспечить возможность **динамически добавлять свойства объекту без создания отдельного класса для каждой комбинации**.

-
Основная структура:

```text
                         <<interface>>
                             Shape
                               △
                               │
                           Polygon
                               │
                 ┌─────────────┼─────────────┐
                 │             │             │
                 ↓             ↓             ↓
          FillDecorator  BorderDecorator  ShadowDecorator
                 △             △             △
                 └─────────────┴─────────────┘
                         реализуют Shape
```

Более точно декоратор должен содержать ссылку на декорируемый объект:

```text
              Shape
                △
                │
        ┌───────┴────────┐
        │                │
     Polygon        ShapeDecorator
                          △
             ┌────────────┼────────────┐
             ↓            ↓            ↓
           Fill        Border        Shadow
```

`ShapeDecorator` хранит ссылку на объект типа `Shape`.


Добавление нового визуального свойства не должно требовать изменения класса `Polygon`.

Например, если в будущем потребуется добавить:

```text
Gradient
Glow
Transparency
Texture
```

должен быть возможен новый декоратор:

```text
GradientDecorator
GlowDecorator
TransparencyDecorator
TextureDecorator
```

без изменения исходной реализации `Polygon`.

Детально [см. декоратор](https://sites.google.com/view/study-pattern/%D0%B3%D0%BB%D0%B0%D0%B2%D0%BD%D0%B0%D1%8F/%D0%B7%D0%B0%D0%B4%D0%B0%D1%87%D0%B8/task-8-%D0%B4%D0%B5%D0%BA%D0%BE%D1%80%D0%B0%D1%82%D0%BE%D1%80)


### Диаграмма последовательностей

Необходимо разработать диаграмму последовательностей для сценария отображения декорированной фигуры.

Например:

```text
Canvas
   │
   │ draw()
   ↓
ShadowDecorator
   │
   │ draw()
   ↓
BorderDecorator
   │
   │ draw()
   ↓
FillDecorator
   │
   │ draw()
   ↓
Polygon
```

Диаграмма должна показывать, как один вызов проходит через цепочку декораторов.

# 2. Архитектурная спецификация

## 2.1. Рисунок

Необходимо выделить объект `Drawing`, содержащий набор объектов изображения.

```text
Drawing
   │
   ├── Pixel
   ├── Polygon
   ├── DecoratedShape
   └── ...
```

`Drawing` отвечает за состав изображения, но не должен зависеть от конкретного способа его хранения в файле.

---

## 2.2. Хранение рисунка

Работу с файлами необходимо отделить от модели рисунка.

Конкретная реализация отвечает за выбранный формат.

Для простоты выберите серилиализацию Java

---

## 2.3. История действий

Для реализации Undo/Redo необходимо хранить историю изменений рисунка.

Один из вариантов архитектуры:

```text
       Action / Command
              │
       ┌──────┴──────┐
       ↓             ↓
     Undo           Redo
     Stack          Stack
```

Каждое значимое действие пользователя должно быть представлено операцией, которую можно выполнить и отменить.



```text
CreateObject
DeleteObject
MoveObject
ChangeProperty
```

---

## 2.4. Настройки

Настройки пользователя должны быть выделены в отдельный объект:

```text
Settings
 ├── backgroundColor
 ├── borderColor
 ├── borderWidth
 └── ...
```

Рабочие компоненты редактора получают значения настроек через соответствующий объект, а не хранят пользовательские параметры самостоятельно.
