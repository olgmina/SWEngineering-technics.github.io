# Задание

Реализовать сбор технических метрик в системе «Цифровой ассистент лектора». 
Система уже имеет базовую функциональность: лектор переключает слайды через консоль, слушатели получают их через Telegram-бота. 
Необходимо добавить мониторинг на сервере презентаций и получение индивидуальных действий пользователя стандарта xAPI.
с использованием Spring Boot и Micrometer. 

Метрики должны сохраняться в Prometheus и быть доступны для визуализации в Grafana (дашборд прилагается). Допускается использование готового docker-compose.yml с Prometheus и Grafana.

Результат должен включать:

 - реализацию сервиса сбора и сохранения метрик

- JUnit-тесты (хотя бы позитивный сценарий)

- Скриншот метрики в Grafana 


## Индивидуальные варианты

### 1. Измерение сетевого трафика 
    
Реализовать перехватчик (интерсептор) для RestTemplate или WebClient, который логирует размер тела каждого запроса к Telegram API и размер ответа. Агрегировать эти значения в Counter Micrometer с тегом lecture_id.
    
Входные данные: RestTemplate для вызовов Telegram API.
    
Ожидаемый результат:
    
- Класс TelegramTrafficInterceptor implements ClientHttpRequestInterceptor
    
- Метрики в Prometheus: telegram.traffic.outbound.bytes и telegram.traffic.inbound.bytes
    
- Метод, возвращающий суммарный трафик за лекцию в МБ
    
*Подсказка*: Используйте body.length для запроса и response.getHeaders().getContentLength() для ответа.

### 2.  Расчёт P95 задержки доставки

Реализовать измерение времени выполнения каждого синхронного вызова к Telegram API с помощью Timer.Sample Micrometer. Записать метрику telegram.api.latency с перцентилями 0.5, 0.95, 0.99.
      
Входные данные: RestTemplate для вызовов Telegram API.
       

Ожидаемый результат:       

В каждом вызове API создаётся Timer.Sample
       
Метрика регистрируется через Timer.builder().publishPercentiles(0.5, 0.95, 0.99)
       
Возможность получить P95 за конкретную лекцию через тег
       
*Подсказка*: Используйте Timer.start(meterRegistry) и sample.stop(timer).

### 3. Подсчёт количества отправленных сообщений

Задача: Реализовать счётчик Counter для каждого типа сообщения (MessageType enum). Добавить проверку на превышение лимита и отправку предупреждения в лог при приближении к порогу.

Входные данные: Сервис отправки сообщений.

Ожидаемый результат:

- Enum MessageType с типами: SLIDE_PUSH, SLIDE_PULL, QUESTION_BROADCAST, POLL, ALERT, CHECKPOINT

- Метод incrementCounter(MessageType type, String lectureId)

- Лог-предупреждение при >18 сообщений в минуту

*Подсказка*: Используйте Counter.builder().tag("type", type.name()).register().

### 4. Мониторинг нагрузки на сервер 

Условие: Разные стратегии рассылки слайдов по-разному нагружают сервер. Нужно измерять загрузку CPU в процентах и привязывать её к текущей лекции, чтобы потом сравнить S1–S5.

Задача: Настроить Spring Boot Actuator + Micrometer для сбора system.cpu.usage. Добавить кастомный Gauge, который будет регистрировать текущую загрузку CPU с тегом lecture_id.

Входные данные: Зависимость micrometer-registry-prometheus в pom.xml.

Ожидаемый результат:

- Эндпоинт /actuator/prometheus доступен и показывает system_cpu_usage

- Собственный Gauge для CPU с тегом лекции

- Метод startMonitoring(lectureId), который привязывает текущее измерение к лекции

*Подсказка*: Используйте Gauge.builder("lecture.cpu.usage", () -> getCurrentCpuLoad()).

### 5. Расчёт коэффициента ошибок доставки 

Не все сообщения успешно доходят до слушателей. Ошибки могут возникать из-за таймаутов, лимитов Telegram или проблем с сетью. Нужно вычислить долю ошибок относительно всех отправленных сообщений.

Реализовать два счётчика: total_messages_sent и total_messages_failed. Коэффициент ошибок вычисляется как failed / total. Добавить алерт при превышении 5% ошибок за лекцию.

Входные данные: Исключения при вызовах Telegram API.

Ожидаемый результат:

- Counter для успешных и не успешных отправок

- Метод recordDeliveryStatus(lectureId, success)

- Сообщение лектору (лог или WebSocket-уведомление лектору) при отношении ошибок > 5%

*Подсказка*: Оборачивайте вызовы API в try-catch; в catch увеличивайте счётчик ошибок.

### 6. Расчёт метрик понятности лекции 
       
В системе «Цифровой ассистент лектора» через Telegram-бота собираются следующие xAPI-события от слушателей:
       
| Тип события (verb) |	Описание |	Данные |
|---|---|---|
|rated|	Оценка понятности слайда	|slide_id, rating (1–5)|
|       asked |	Вопрос по слайду |	slide_id, question_text |
| answered	| Ответ на тест/опрос |	quiz_id, answer, is_correct |

На основе этих данных рассчитать метрики понятности лекции:
       
 Clarity Rating (CR) — средняя оценка понятности слайда
       
 Question Density (QD) — количество вопросов на один слайд в расчёте на одного активного слушателя
       
 Question Temporal Depth (QTD) — среднее время между появлением слайда и вопросом по нему


### 7. Измерение активности лектора 

Частота действий лектора (переключение слайдов, аннотации, запуск опросов) влияет на нагрузку системы и на восприятие лекции слушателями. Нужно измерять количество действий в минуту и классифицировать их по типам.

Реализовать счётчик действий лектора через WebSocket-события от консоли. Для каждого типа действия (NEXT_SLIDE, ADD_ANNOTATION, START_POLL, LAUNCH_QUIZ) инкрементировать соответствующий счётчик и вычислять частоту в минуту за последние 5 минут.

Входные данные: WebSocket-сообщения от приложения лектора.

Ожидаемый результат:

- Map<ActionType, AtomicLong> для счётчиков

- Метод recordAction(ActionType type, String lectureId)

- Метод getActionsPerMinute(lectureId, windowMinutes), возвращающий частоту по каждому типу

*Подсказка*: Используйте ScheduledExecutorService для очистки старых событий и пересчёта частоты.
