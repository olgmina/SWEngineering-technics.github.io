# Вегас (Игровой дом)

**Цель проекта:** научиться интегрировать независимо разработанные компоненты, согласовывать интерфейсы и правила командной работы, выделять общую ответственность и развивать архитектуру при появлении новых требований.

>Разработан индивидуальный игровой автомат по заданию [«Цепочка обязанностей»](https://sites.google.com/view/study-pattern/главная/задачи/task-14-цепочка-обязанностей). В исходной программе реализованы пользовательский интерфейс, игровой цикл, обработка выигрыша и проигрыша, собственный учёт монет игрока. **Повторно разрабатывать автомат не требуется.** Существующий код считается унаследованной системой, которую необходимо включить в совместный проект.

Проект проходит три этапа:

1. **Объединение автоматов** — согласование интерфейса и правил совместной разработки; каталог и запуск автоматов.
2. **Общий игровой баланс** — выделение менеджера баланса, согласование взаимодействия компонентов и распределение командных ролей.
3. **Стратегии азарта игрового зала** — добавление общих правил по индивидуальным вариантам без изменения внутренней игровой логики автоматов.

Практики программной инженерии:

- **проектирование:** границы компонентов, интерфейсы, UML-диаграммы классов и последовательностей, распределение ответственности;
- **командная работа:** Git, ветки, Pull Request, проверка кода, роли и ответственность участников;
- **интеграция:** адаптеры, контракты, совместимость версий, интеграционные испытания;
- **качество:** критерии приёмки, тесты, регрессионные проверки;
- **документация:** README, CHANGELOG, каталог `docs/`, решения об архитектуре.

**Ограничения учебной модели.** Используются условные игровые монеты, без реальных платежей. На втором инкременте достаточно одного игрока и последовательного запуска автоматов. Сетевая архитектура, база данных и многопоточность не требуются. В третьем инкременте стратегии изменяют только правила начисления бонусов и доступные игровые предложения, а не скрыто управляют вероятностью выигрыша.

# Интеграция 1. Объединение игровых автоматов

**Цель:** спроектировать единый интерфейс взаимодействия с автоматами и согласовать правила коллективной разработки.

**Архитектурная проблема.** Каждый автомат запускается и завершается по-своему; способы получения названия, отображения окна и передачи результата различаются. Прямое включение всех программ в главное приложение приведёт к множеству зависимостей от конкретных реализаций.

## 1. Функциональные требования

| ID | Функциональное требование | Описание | Критерий приёмки |
|---|---|---|---|
| **FR-1.1** | Каталог автоматов | Главное приложение показывает подключённые автоматы | В списке видны названия не менее двух независимо разработанных автоматов |
| **FR-1.2** | Выбор автомата | Пользователь выбирает автомат из каталога | Выбранный автомат запускается без изменения кода главного приложения |
| **FR-1.3** | Возврат в каталог | После завершения игры пользователь может выбрать другую | Каталог вновь доступен без перезапуска приложения |
| **FR-1.4** | Общий контракт | Все автоматы доступны через согласованный интерфейс | Главное приложение не обращается к классам конкретных игр |
| **FR-1.5** | Добавление автомата | Новый автомат подключается по установленным правилам | Подключение не требует изменения логики уже подключённых автоматов |
| **FR-1.6** | Обработка отказа | Ошибка запуска одного автомата не завершает весь игровой зал | Показано сообщение об ошибке, каталог остаётся доступен |

## 2. Архитектурная спецификация

Предлагается выделить следующие компоненты:

```text
                    GameHall
                       |
                  GameCatalog
                       |
                 <<interface>>
                   GameMachine
                  /     |     \
                 /      |      \
             AdapterA AdapterB AdapterC
                |        |        |
             GameA    GameB    GameC
```

`GameHall` не должен знать внутренние классы автоматов. **Общий интерфейс проектирует команда**, а не получает готовым от преподавателя. При необходимости используется паттерн **Адаптер**, чтобы сохранить исходный код автомата.

Минимальные вопросы для согласования контракта:

- Как узнать название автомата и показать его в каталоге?
- Как запустить игру и определить, что она завершилась?
- Кто управляет отображением и закрытием игрового окна?
- Как сообщить об ошибке запуска?
- Какие сведения о результате потребуются в следующем инкременте?

**Задание на проектирование:** составьте таблицу различий исходных реализаций, предложите общий интерфейс Java и постройте UML-диаграмму классов. Зафиксируйте договорённость об интерфейсе в `docs/integration-contract.md`. Не следует преждевременно включать управление балансом в интерфейс первого инкремента.

# Модификация. Общий игровой баланс и распределение ответственности

**Цель:** спроектировать единый менеджер игрового баланса, организовать согласованную работу компонентов и распределить роли участников команды.

**Архитектурная проблема.** Автоматы уже объединены, но каждый самостоятельно хранит и изменяет количество монет. При переходе между играми единый баланс отсутствует. Если каждый автомат продолжит изменять счёт напрямую, состояние игрока станет несогласованным.

## 1. Функциональные требования

| ID | Функциональное требование | Описание | Критерий приёмки |
|---|---|---|---|
| **FR-2.1** | Единый баланс | Все автоматы используют один счёт игрока | После перехода в другой автомат отображается актуальный баланс |
| **FR-2.2** | Ставка | Перед игровым раундом списывается согласованная ставка | При достаточном балансе сумма списывается ровно один раз |
| **FR-2.3** | Недостаток монет | Раунд не начинается без достаточного количества монет | Баланс не становится отрицательным |
| **FR-2.4** | Начисление выигрыша | После завершения раунда выигрыш зачисляется на общий счёт | Баланс увеличивается на указанную сумму ровно один раз |
| **FR-2.5** | Отображение баланса | Игрок видит текущий счёт | Отображаемая сумма соответствует данным менеджера |
| **FR-2.6** | Согласованное завершение | Отмена или ошибка не создаёт повторных списаний и начислений | Баланс соответствует принятому командой правилу обработки отмены |
| **FR-2.7** | Сохранение функциональности | Автоматы сохраняют прежнюю игровую механику | Игры работают через общий менеджер без изменения правил розыгрыша |

## 2. Архитектурная спецификация

Предлагается **самое простое решение**: один объект `BalanceManager`, один счёт, последовательные игровые раунды. Состояние хранится в памяти. Для учебного проекта не требуются база данных, потоки и сетевые транзакции.

```text
                 GameHall
                    |
             GameCoordinator
              /           \
             /             \
       GameMachine      BalanceManager
             |                |
         GameResult       balance: int
```

**Принцип:** только `BalanceManager` изменяет общий баланс. Автомат сообщает исход раунда, но не получает прямого доступа к изменяемому счёту.

Пример контракта для обсуждения (не обязательная готовая реализация):

```java
public record GameResult(int prize) { }

public final class BalanceManager {
    private int balance;

    public BalanceManager(int initialBalance) {
        if (initialBalance < 0) throw new IllegalArgumentException();
        balance = initialBalance;
    }

    public int getBalance() { return balance; }

    public boolean tryPlaceBet(int amount) {
        if (amount <= 0) throw new IllegalArgumentException();
        if (amount > balance) return false;
        balance -= amount;
        return true;
    }

    public void addPrize(int amount) {
        if (amount < 0) throw new IllegalArgumentException();
        balance = Math.addExact(balance, amount);
    }
}
```

В этой модели **один раунд — одна ставка и один результат**. Координатор разрешает только один активный раунд, списывает ставку, запускает раунд и после получения результата однократно начисляет выигрыш. При ошибке или отмене до получения результата команда должна выбрать и документировать правило возврата ставки. Проверку «ровно один раз» обеспечивает координатор; приведённый менеджер баланса сам по себе не защищает от повторного вызова.

**Необходимо спроектировать:**

1. UML-диаграмму классов с границами ответственности.
2. Диаграмму последовательностей «выбор автомата → ставка → раунд → результат → начисление → возврат в каталог».
3. Правила обработки отмены, ошибки и повторного сообщения о результате.
4. Изменения общего интерфейса и порядок перехода автоматов на новую версию контракта.

## 3. Командные роли и организация работ

На этом этапе команда должна **явно распределить ответственность**. Роли не обязательно соответствуют отдельным людям: в малой команде участник может совмещать роли, но для каждой задачи должен быть назначен ответственный.

| Роль | Ответственность | Результат работы |

| Архитектор | Согласование компонентов, интерфейсов, архитектурных решений | UML и описание контракта |
| Разработчик менеджера баланса | Реализация и модульные тесты общего счёта | `BalanceManager` и тесты |
| Разработчики автоматов | Адаптация индивидуальных игр к новому контракту | Совместимые модули |
| Интегратор | Сборка, подключение модулей, разрешение конфликтов | Рабочая общая сборка |

**Задание команде:** создайте таблицу распределения задач «задача — ответственный — проверяющий — состояние». Каждый студент должен внести проверяемый вклад в общий проект, а не только участвовать в обсуждениях. Решения об интерфейсе и спорные изменения фиксируются в репозитории.

## 4. Реализация и инженерные практики

# Инкремент 3. Стратегии азарта игрового зала

**Цель:** реализовать дополнительные требования к игровому залу, научиться расширять общую архитектуру и интегрировать индивидуально разработанные стратегии.

**Архитектурная проблема.** Владелец игрового зала вводит дополнительные правила поощрения игрока. Эти правила действуют **на уровне всего зала**, а не конкретного автомата. Например, серия побед может включать результаты разных игр. Если внедрить бонусную логику в каждый автомат, изменения придётся дублировать и согласовывать во всех модулях.

## 1. Функциональные требования

| ID | Функциональное требование | Описание | Критерий приёмки |
|---|---|---|---|
| **FR-3.1** | Общая стратегия | Правила поощрения применяются ко всем подключённым автоматам | Стратегия работает при переходе между играми |
| **FR-3.2** | Выбор стратегии | Игровой зал позволяет выбрать одну из подключённых стратегий | Выбранное правило применяется к последующим раундам |
| **FR-3.3** | Бонусы | Стратегия может предложить бонус по результатам игры | Бонус рассчитан по правилам стратегии и начислен один раз |
| **FR-3.4** | История раундов | Стратегия получает необходимые сведения о ранее завершённых раундах | Результат не зависит от того, какой автомат сформировал событие |
| **FR-3.5** | Независимость автоматов | Автоматы не знают о конкретных стратегиях | Добавление стратегии не требует изменения кода игровых автоматов |
| **FR-3.6** | Расширяемость | Новая стратегия подключается через общий контракт | Добавление варианта не требует изменения уже существующих стратегий |
| **FR-3.7** | Регрессионная совместимость | Базовый игровой процесс и баланс продолжают работать | Тесты первых двух инкрементов выполняются успешно |

## 2. Архитектурная спецификация

**Предлагаемая идея:** отделить обычный результат игрового раунда от бонуса, который рассчитывает игровая система. Стратегия получает сведения о завершённом раунде и, если нужно, о предыдущих раундах, возвращает **предложение о бонусе**. Изменяет баланс только `BalanceManager` через координатор.

```text
                   GameHall
                      |
                GameCoordinator
                /      |       \
               /       |        \
       GameMachine  GameHistory  <<interface>>
            |           |       HallStrategy
        GameResult      |        /   |   \
            \           |       /    |    \
             \          |    BonusA BonusB BonusC
              \         |        /
               \        |       /
                BalanceManager
```

Схема показывает логические зависимости; стратегия **не должна напрямую** изменять баланс. Координатор получает решение стратегии, проверяет его и передаёт начисление менеджеру.

Для обсуждения можно использовать такой минимальный контракт:

```java
public interface HallStrategy {
    String getName();
    int calculateBonus(RoundResult current, GameHistory history);
}
```

`RoundResult` — единое описание завершённого раунда (идентификатор, автомат, ставка, основной приз, исход). `GameHistory` — доступ к уже завершённым раундам. Форму этих типов проектирует команда. Для предотвращения повторного бонуса координатор должен обрабатывать каждый идентификатор раунда один раз. В учебной версии достаточно хранить историю в памяти.

**Обязательное архитектурное ограничение:** стратегия не меняет внутренний механизм розыгрыша и не назначает скрытые вероятности выигрыша. Она определяет прозрачные дополнительные бонусные правила, применимые к любому автомату. В один момент активна одна стратегия; комбинирование нескольких стратегий не требуется.

## 3. Индивидуальные варианты стратегий

**Каждый студент разрабатывает один вариант** на основе общего интерфейса. Варианты различаются правилами, но не требуют изменения автоматов.

| № | Вариант | Правило начисления бонуса | Проверяемая особенность |
|---|---|---|---|
| 1 | Серия побед | После трёх выигрышных раундов подряд — бонус 3 монеты | Серия сохраняется при смене автомата |
| 2 | Утешительный бонус | После четырёх проигрышей подряд — бонус 1 монета | Выигрыш сбрасывает счётчик проигрышей |
| 3 | Первое знакомство | За первый завершённый раунд на каждом новом автомате — бонус 1 монета | Повторная игра на том же автомате не даёт бонус |
| 4 | Исследователь | После игры на трёх различных автоматах — бонус 4 монеты | Учитываются уникальные автоматы |
| 5 | Постоянный посетитель | За каждый пятый завершённый раунд — бонус 2 монеты | Начисления на 5-м, 10-м, 15-м раундах |
| 6 | Чередование | За три раунда подряд на разных автоматах — бонус 2 монеты | Повтор одного автомата нарушает серию |
| 7 | Крупный выигрыш | Если основной приз раунда не меньше 10 монет — бонус 2 монеты | Порог проверяется до начисления бонуса |
| 8 | Возврат к игре | Если после двух проигрышей следует выигрыш — бонус 2 монеты | Учитывается порядок исходов |
| 9 | Малые ставки | После трёх раундов подряд со ставкой 1 монета — бонус 1 монета | Ставки из разных автоматов учитываются вместе |
| 10 | Коллекционер побед | За победы на трёх разных автоматах — бонус 5 монет | Победа на одном автомате учитывается один раз |
| 11 | Ровный счёт | Если после обычного начисления приза баланс кратен 10 — бонус 1 монета | Проверяется баланс до бонуса стратегии |
| 12 | Первый успех | За первую победу за сеанс — бонус 3 монеты | Повторная победа не даёт бонус |

**Общие правила вариантов:** все бонусы начисляются только после завершённого раунда; достижение порога серии не должно повторно награждаться за тот же раунд; стратегии 3, 4, 10 и 12 выдают соответствующее достижение однократно за сеанс. Для остальных серий команда документирует правило сброса или повторного начисления. Если автомат не предоставляет данные, необходимые варианту (например, размер ставки), сначала согласуется расширение **общего контракта**, а не добавляется специальный вызов к конкретной игре.

При большом числе студентов допустимы повторные варианты, но с разными параметрами, отдельными тестами и независимой реализацией.

## 4. Реализация и инженерные практики

1. Команда согласует формат `RoundResult`, историю раундов и интерфейс `HallStrategy`.
2. Каждый студент выбирает или получает индивидуальный вариант стратегии.
3. Студент составляет UML-диаграмму своего решения и тесты граничных случаев.
4. Реализует стратегию в отдельной ветке, не изменяя игровые автоматы.
5. Интегратор подключает стратегии к общему каталогу правил игрового зала.
6. Проводятся интеграционные и регрессионные испытания.
7. Команда оценивает, какие изменения потребовались для подключения новой стратегии, и обновляет документацию.

## 5. Проверка соответствия

| ID | Уровень | Проверяем | Действие | Ожидаемый результат |
|---|---|---|---|---|
| T3.1 | Unit | Индивидуальная стратегия | Передать историю, удовлетворяющую правилу | Возвращён ожидаемый бонус |
| T3.2 | Unit | Отсутствие основания | Передать историю без достижения условия | Бонус равен нулю |
| T3.3 | Unit | Граница условия | Проверить историю до и после достижения порога | Бонус возникает в нужный момент |
| T3.4 | Integration | Общая история | Провести раунды на разных автоматах | Стратегия учитывает все результаты |
| T3.5 | Integration | Единственный бонус | Повторно обработать тот же раунд | Бонус не начислен повторно |
| T3.6 | Integration | Смена стратегии | Выбрать другой вариант перед следующим раундом | Применяется новая стратегия; прошлые бонусы не пересчитываются |
| T3.7 | Regression | Предыдущие инкременты | Запустить тесты 1 и 2 | Все ранее принятые функции работают |
| AT3.1 | Acceptance | Расширяемость | Подключить новую индивидуальную стратегию | Код игровых автоматов не меняется |

**Вопросы для обсуждения:** Почему стратегия относится к игровому залу, а не к автомату? Как отделить вычисление бонуса от изменения баланса? Как предотвратить повторное начисление? Какие изменения архитектуры оказались необходимы и какие удалось избежать?

## Критерии оценивания

| Критерий | Балл |
|---|---:|
| Обоснованность интерфейсов и архитектуры | 1 |
| Корректность интеграции и сохранение функциональности | 1 |

**На защите каждый студент** демонстрирует свой вклад, объясняет принятое архитектурное решение и показывает проверку его работы в общей системе. Команда отдельно демонстрирует сквозной сценарий: выбор автомата → ставка → раунд → общий баланс → стратегия бонуса → переход к другому автомату.
