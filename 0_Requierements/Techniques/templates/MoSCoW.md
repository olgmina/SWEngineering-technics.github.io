# Приоритеты требований (MoSCoW)

MoSCoW представляет собой метод приоритизации требований, широко используемый в гибкой разработке (Agile), и его цель — распределить требования по степени важности, чтобы эффективно управлять ограниченными ресурсами (временем, бюджетом, командой).

## Назначение метода MoSCoW

Метод MoSCoW позволяет решать следующие задачи:

- выделить критически важные функции, без которых продукт не имеет смысла;
- определить функции, которые можно отложить на следующие версии;
- согласовать ожидания заказчика и команды разработки;
- принимать обоснованные решения при нехватке времени или ресурсов;
- фокусироваться на действительно важном, избегая «распыления» на второстепенные задачи.

| Буква | Английский термин | Русский перевод | Значение |
|-------|-------------------|-----------------|----------|
| **M** | **Must have** | **Обязательно** | Критически важные функции. Без них продукт неработоспособен или не имеет смысла |
| **S** | **Should have** | **Следует иметь** | Важные функции, но можно найти временный обходной путь |
| **C** | **Could have** | **Можно иметь** | Приятные дополнения, реализуются при наличии времени/ресурсов |
| **W** | **Won't have** | **Не будет (в этой версии)** | Сознательно отложенные или исключенные функции |

> **Важно:** Буквы в аббревиатуре **не образуют слово** — заглавные буквы просто выбраны для удобства запоминания. Буква «o» в MoSCoW не означает ничего и добавлена для благозвучия.

## Описание категорий приоритетов

### Must have (Обязательно)

Функции, без которых продукт **не может быть выпущен**. Их отсутствие делает продукт бесполезным или критически уязвимым.

**Признаки Must have:**

- Без этой функции продукт не решает основную проблему пользователя
- Отсутствие делает невозможным использование других функций
- Требование связано с безопасностью или соответствием законодательству

**Примеры:**

- «Авторизация пользователя» — без неё нет персонализации
- «Сохранение заказа» — иначе заказ не будет оформлен

### Should have (Следует иметь)

Важные функции, которые **должны быть реализованы**, но при острой нехватке времени можно найти временное решение.

**Признаки Should have:**

- Функция важна, но есть обходной путь
- Её отсутствие ухудшает качество, но не делает продукт бесполезным
- Можно реализовать в следующей итерации

**Примеры:**

- «Уведомления по email» — можно дублировать в интерфейсе
- «Экспорт в Excel» — можно скопировать данные вручную

### Could have (Можно иметь)

Желательные функции, которые **реализуются при наличии ресурсов**. Их отсутствие не влияет на выпуск продукта.

**Признаки Could have:**

- Функция улучшает продукт, но не является критической
- Легко отложить на следующий релиз
- Часто это «плюшки» и приятные дополнения

**Примеры:**

- «Тёмная тема интерфейса» — приятно, но не обязательно
- «Интеграция с Telegram» — можно использовать веб-версию

### Won't have (Не будет в этой версии)

Функции, которые **сознательно исключены** из текущей версии. Они могут быть реализованы в будущем или отвергнуты полностью.

**Признаки Won't have:**

- Функция требует слишком много ресурсов
- Не соответствует текущей стратегии продукта
- Может быть реализована в следующих релизах

**Примеры:**

- «Мобильное приложение» — отложено на версию 2.0
- «Голосовой ввод» — не соответствует целевой аудитории

## Порядок определения приоритетов

Приоритизация требований методом MoSCoW выполняется в следующем порядке:

1. **Составьте полный список требований** (из матрицы классификации или сценариев использования)
2. **Для каждого требования ответьте на вопросы:**
   - Что произойдёт, если этого не будет?
   - Есть ли обходной путь?
   - Сколько времени/ресурсов потребуется?
3. **Назначьте приоритет** по таблице ниже
4. **Проверьте баланс** — Must have должно составлять не более 60% от всех требований
5. **Согласуйте приоритеты** с заказчиком или преподавателем

## Критерии назначения приоритетов

| Приоритет | Ключевой вопрос | Что если не сделаем? | Доля от всех требований |
|-----------|-----------------|---------------------|------------------------|
| **Must** | «Без этого можно выпускать продукт?» | Продукт не работает | 40-60% |
| **Should** | «Есть ли обходной путь?» | Неудобно, но можно жить | 20-30% |
| **Could** | «Это действительно нужно прямо сейчас?» | Немного хуже, но терпимо | 10-20% |
| **Won't** | «Можно отложить на следующий релиз?» | Ничего страшного | оставшееся |

## Пример использования

*Пример для системы управления проектами*

| ID | Требование | Приоритет | Обоснование |
|----|------------|-----------|-------------|
| FR-01 | Создать задачу | **Must** | Без задач нет смысла в системе |
| FR-02 | Редактировать свою задачу | **Must** | Пользователь должен исправлять ошибки |
| FR-03 | Авторизация пользователя | **Must** | Без входа нет персонализации |
| FR-04 | Назначить исполнителя | **Should** | Можно начать с одного пользователя |
| FR-05 | Уведомления по email | **Could** | Удобно, но не критично для MVP |
| FR-06 | Экспорт в Excel | **Could** | Можно скопировать данные вручную |
| FR-07 | Интеграция с Telegram | **Won't** | Отложено на версию 2.0 |
| FR-08 | Тёмная тема | **Won't** | Не соответствует текущим приоритетам |

## Проверка баланса

После назначения приоритетов необходимо проверить баланс:

**Исходные данные (из примера выше):**
- Всего требований: 8
- Must have: 3 (38%)
- Should have: 1 (12%)
- Could have: 2 (25%)
- Won't have: 2 (25%)

**Вывод:** Баланс соблюдён. Must have не превышает 60%, есть резерв для Should и Could.

## Типичные ошибки

| Ошибка | Описание | Как исправить |
|--------|----------|---------------|
| **Всё — Must** | Студент ставит высший приоритет всем требованиям | Ввести ограничение: не более 60% Must |
| **Путаница Should и Could** | Важные функции попадают в Could | Задать вопрос: «Есть ли обходной путь?» |
| **Нет обоснования** | Приоритет назначен без причины | Требовать письменное обоснование каждого приоритета |
| **Won't отсутствуют** | Нет отложенных функций | Сознательное планирование следующей версии |
