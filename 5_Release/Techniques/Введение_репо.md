# Практика. Ведение репозитория и документации проекта

## Цель

Научиться поддерживать репозиторий программного проекта в состоянии, пригодном для дальнейшей разработки и передачи другому разработчику.

Главный принцип:

> **Документация и репозиторий должны соответствовать текущему состоянию программы.**

---

# 1. Структура репозитория

В начале работы проверьте структуру проекта.

Рекомендуется:

```text
GraphEditor/
│
├── src/
│   └── ...
│
├── test/
│   └── ...
│
├── docs/
│   ├── architecture/
│   ├── uml/
│   └── images/
│
├── README.md
├── CHANGELOG.md
├── .gitignore
└── ...
```

Конкретная структура может зависеть от используемой среды разработки.

### Задание

Создайте каталоги:

```text
docs/
docs/uml/
docs/images/
```

Переместите архитектурные рисунки проекта в соответствующие каталоги.

---

# 2. Настройка `.gitignore`

В репозитории не должны храниться файлы, которые создаются средой разработки или процессом сборки и не являются частью исходного проекта.

Для Java-проекта необходимо определить, какие файлы следует исключить.

Например:

```text
target/
out/
*.class
.idea/
*.iml
```

Набор зависит от используемой среды разработки и системы сборки.

## Задание

1. Определите файлы и каталоги, которые не должны попадать в Git.
2. Добавьте их в `.gitignore`.
3. Проверьте:

```bash
git status
```

В рабочем каталоге не должны появляться файлы среды разработки и результаты сборки.

### Вопрос

Почему `.gitignore` не является способом удалить уже попавший в репозиторий файл?

---

# 3. Организация документации

В первом инкременте была создана базовая документация проекта.

Во втором инкременте необходимо организовать её хранение.

Разместите в `docs/`:

- диаграмму классов;
- диаграмму последовательностей;
- архитектурную схему;
- дополнительные рисунки, необходимые для понимания проекта.

Например:

```text
docs/
├── uml/
│   ├── classes-v1.png
│   ├── classes-v2.png
│   └── sequence-v2.png
│
└── images/
    └── architecture-v2.png
```

Названия файлов должны позволять определить их назначение.

---

# 4. README как документация продукта

README должен позволять человеку, который впервые открыл репозиторий, понять:

1. что это за проект;
2. что он умеет;
3. как его запустить;
4. как устроен проект;
5. какая версия сейчас представлена.

## Задание

Актуализируйте README.

Рекомендуемая структура:

```text
# GraphEditor

## Назначение

## Возможности

## Требования

## Запуск

## Структура проекта

## Архитектура

## Документация

## История изменений
```

---

# 5. Добавление рисунков в README

Диаграммы и изображения должны быть доступны непосредственно из документации.

Например:

```markdown
## Архитектура

![Архитектура проекта](docs/images/architecture-v2.png)
```

Или:

```markdown
## UML

![Диаграмма классов](docs/uml/classes-v2.png)
```

### Задание

Добавьте в README:

- изображение архитектуры;
- диаграмму классов;
- при необходимости диаграмму последовательностей.

Проверьте, что изображения корректно отображаются при просмотре README в GitHub.

---

# 6. Актуализация документации

Во втором инкременте архитектура изменилась.

Поэтому документация первого инкремента больше не является полностью актуальной.

### Задание

Сравните документацию с текущей программой.

Найдите:

- устаревшие описания;
- отсутствующие классы;
- отсутствующие возможности;
- устаревшие рисунки.

Обновите документацию.

### Важный принцип

Не нужно создавать новую документацию вместо старой только потому, что изменилась программа.

Необходимо **актуализировать существующую документацию**.

---

# 7. CHANGELOG

Создайте файл:

```text
CHANGELOG.md
```

Он должен содержать историю изменений продукта.

Например:

```markdown
# История изменений

## [0.2.0]

### Добавлено

- Векторные фигуры
- Полигоны
- Заливка
- Контур
- Тень
- Подсказки инструментов

### Изменено

- Обновлена архитектура редактора
- Обновлена документация

## [0.1.0]

### Добавлено

- Растровое рисование
- Точка
- Круг
- Квадрат
- Фабрика элементов
```

## Задание

Добавьте в CHANGELOG изменения второго инкремента.

Необходимо разделить:

- новые возможности;
- изменения существующих возможностей;
- исправления ошибок.

---

# 8. Задачи проекта

Каждая значимая функция второго инкремента должна быть оформлена как отдельная задача.

Например:

```text
Issue #10
Добавить полигон

Issue #11
Добавить заливку

Issue #12
Добавить контур

Issue #13
Добавить тень
```

В задаче необходимо указать:

- что требуется сделать;
- ожидаемый результат;
- при необходимости критерии приёмки.

### Задание

Создайте задачи для основных функций второго инкремента.

---

# 9. Связь задачи, ветки и Pull Request

Для каждой задачи должна существовать соответствующая ветка.

Например:

```text
Issue #11
   ↓
feature/fill
   ↓
Commits
   ↓
Pull Request
   ↓
Code Review
   ↓
Merge
```

В Pull Request необходимо указать, какую задачу он решает.

Описание должно содержать:

```text
Что сделано

Как проверить

Какие файлы изменены

Какие тесты добавлены
```

---

# 10. Проверка документации при Code Review

При проверке Pull Request необходимо проверить не только исходный код.

Дополнительно проверить:

- обновлён ли README;
- добавлены ли необходимые рисунки;
- актуальна ли UML;
- обновлён ли CHANGELOG;
- не появились ли лишние файлы;
- соответствует ли `.gitignore` проекту;
- изменились ли тесты вместе с функциональностью.

Таким образом, Code Review проверяет **изменение программного продукта целиком**, а не только исходный код.

---

# 11. Версия проекта

После завершения второго инкремента необходимо зафиксировать версию продукта.

Например:

```text
v0.2.0
```

Версия должна быть указана:

- в Release;
- в CHANGELOG;
- при необходимости в README.

Создайте Git-тег:

```bash
git tag v0.2.0
```

Проверьте:

```bash
git tag
```

---

# 12. Release

Создайте Release для второго инкремента.

В описании укажите:

### Новые возможности

- полигон;
- заливка;
- контур;
- тень;
- подсказки.

### Архитектурные изменения

- введена общая модель `Shape`;
- добавлен механизм декорации;
- обновлена архитектура редактора.

### Проверка

- добавлены тесты;
- пройдены регрессионные тесты первого инкремента.

---

# 13. Проверка содержимого репозитория

Перед завершением второго инкремента выполните:

```bash
git status
```

```bash
git log --oneline --graph --all
```

```bash
git tag
```

Проверьте репозиторий целиком.

В нём должны находиться:

```text
GraphEditor/
│
├── src/
├── test/
├── docs/
│   ├── uml/
│   └── images/
│
├── README.md
├── CHANGELOG.md
└── .gitignore
```

| README актуализирован | ☐ |
| README содержит рисунки | ☐ |
| Ссылки на рисунки работают | ☐ |
| Создан CHANGELOG | ☐ |
| CHANGELOG содержит изменения второго инкремента | ☐ |
| Для функций созданы задачи | ☐ |
| Pull Request содержит описание изменений | ☐ |
| Code Review выполнен | ☐ |
| Создан тег версии | ☐ |
| Создан Release | ☐ |
| Регрессионные тесты пройдены | ☐ |
