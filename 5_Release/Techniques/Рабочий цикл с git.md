# Практика постоянной работы с git

## Тема 2.1 [Ветвления](SWEngineering-technics.github.io&path=5_Release/Techniques/Ветвления.md)

Ветвление (branching) — одна из самых мощных функций Git, позволяющая разработчикам создавать независимые линии разработки. Это краеугольный камень гибких рабочих процессов, обеспечивающий изоляцию экспериментальных изменений, параллельную работу над разными задачами и безопасное внедрение новых функций 


## Задача А. Инициализация репозитория и первый коммит

Создайте новую папку для проекта.

Выполните `git init` для создания локального репозитория.

Создайте текстовый файл (например, README.md), добавьте в него текст.

Используйте `git add` для добавления файла в индекс.

Сделайте первый коммит с осмысленным сообщением: `git commit -m "Первый коммит: добавлен README"`.


## Задача Б. Создание и переключение веток
             
1. Создайте новую ветку: git branch feature.
             
2. Переключитесь на неё: git checkout feature.
             
3. Внесите изменения в файл, сделайте коммит.
             
4. Вернитесь в основную ветку: git checkout main.
             
5. Посмотрите разницу между ветками с помощью git diff feature.
  
             
## Алгоритм совместной работы с git

*Создание ветки (branch)*

От основной ветки (обычно main или master) создаётся новая ветка с коротким, описательным названием, например, add-login-feature или fix-typo.

Ветка создаёт отдельное пространство для работы, не затрагивая основную версию проекта.

*Внесение изменений*

На своей ветке разработчик делает необходимые изменения: создаёт, редактирует или удаляет файлы.

Изменения коммитятся поэтапно с понятными сообщениями (примеры: «исправлена ошибка проверки пароля», «добавлен тест для формы регистрации»).

Каждый коммит должен содержать изолированное изменение для упрощения понимания и возможного отката.

*Публикация изменений*

Разработчик отправляет (push) свою ветку на удалённый репозиторий (например, GitHub).

Это резервирует работу в удалённом хранилище, позволяет другим видеть прогресс и участвовать в обсуждении.

*Создание pull request (запроса на слияние)*

Разработчик создаёт pull request, где описывает суть изменений и проблему, которую они решают.

В pull request можно добавлять комментарии, изображения, ссылки на связанные задачи/баги.

Это приглашение к обзору кода со стороны команды — важный этап качества.

*Обсуждение и правки*

Рецензенты просматривают изменения, оставляют комментарии и вопросы.

Разработчик вносит правки, коммитит и пушит их — pull request автоматически обновляется.

Обсуждение продолжается до достижения консенсуса по качеству и функционалу.

*Слияние ветки (merge)*

После одобрения pull request мерджится в основную ветку.

Если возникают конфликты с основным кодом — их нужно разрешить до слияния.

История pull request сохраняется вместе с комментариями и коммитами.

*Удаление ветки*

После успешного слияния удаляется ветка, чтобы избежать путаницы и поддерживать чистоту репозитория.

Вся история изменений остаётся в основной ветке и в pull request.

## Задача С. Откат изменений
             
1. Измените файл, но не добавляйте в индекс.
             
2. Используйте git checkout -- <filename> чтобы отменить изменения.
             
3. Попробуйте откатить последний коммит с помощью git reset --soft HEAD~1.

## Указания по именованию коммитов в Git (на основе лучших практик и соглашения Conventional Commits)
   
  1. Используйте структурированный формат заголовка
  
   
   <   тип    >    (   <   область   >   )   :   <   описание   >   <тип>(<область>):<описание>
   
   где:
   
   *тип* — идентификатор типа изменений (например, feat — новая функциональность, fix — исправление ошибки, docs — документация, style — оформление кода, refactor — рефакторинг).
   
   *область (опционально)* — часть проекта или компонент, в которой сделаны изменения (например, login, api).
   
   *описание* — краткое резюме действия в повелительном наклонении и в настоящем времени (например, add user authentication, а не added user authentication).
   
2. Заголовок должен быть коротким и ёмким
   
   Оптимальная длина — до 50 символов, максимум 72.
   
   Не добавляйте точку в конце.
   
3. Начинайте заголовок с маленькой буквы (кроме имён и аббревиатур).
   
   Пишите тело коммита (необязательно)
   
   Если изменения сложные, укажите подробное описание «почему» и «что» было сделано.
   
   Тело отделяется пустой строкой от заголовка.
   
   Добавляйте футеры для важной информации (необязательно)
   
   Например, ссылки на задачи, отметки о breaking changes.
   
   Формат: Closes #123, BREAKING CHANGE: ...
   
   Примеры корректных коммитов
   
   ``
   feat(auth): add user login feature
      fix(api): correct response format for error cases
      
      docs(readme): update installation instructions
      
      refactor(ui): improve layout responsiveness
   ``
   
   *Общие рекомендации*
   
   Используйте английский язык (если это принято в проекте).
   
   Пишите в повелительном наклонении: «fix bug», «add test», а не «fixed bug» или «adding test» (Например, исправлены ошибки или добавлен тест).
   
   Делайте коммиты небольшими и логичными, чтобы их было легко читать и при необходимости откатывать.
